# Этап 1: синхронное уведомление

Замер выполнен 5 ноября 2026 года, 16:24 МСК, на локальном NestJS-приложении
с настоящим PostgreSQL 17 в Docker. E2E использует отдельную временную БД
с применёнными миграциями. Время измеряется через `performance.now()` вокруг
HTTP-запросов Supertest и округляется до миллисекунд.

## Результаты

| Операция                                                        | Время, мс |
| --------------------------------------------------------------- | --------: |
| `POST /orders` без ожидания email                               |        36 |
| `POST /orders` с реальным ожиданием email                       |      3009 |
| Разница времени ответа                                          |      2973 |
| `GET /orders/:id` во время ожидания email                       |         4 |
| Блокировка строки товара из другой транзакции во время ожидания |         2 |

Это один сравнительный прогон. В базовом запросе только метод отправки email
временно заменён на немедленное успешное завершение через
`mockResolvedValueOnce(undefined)`. HTTP-обработка, валидация, транзакция,
запись заказа и списание остатков настоящие в обоих запросах.
Во втором запросе работает настоящий `NotificationsService` с таймером 3000 мс;
ускорение или подмена таймеров не используются.

## Что проверено

До завершения второго `POST` тест дожидается начала уведомления и читает заказ
через отдельный HTTP-запрос. Полученный заказ совпадает с последующим ответом
`POST`: запись уже закоммичена и видна другим соединениям.

В тот же период другая транзакция успешно выполняет
`SELECT id FROM "Product" WHERE id = 11 FOR UPDATE NOWAIT`.
Если бы исходная транзакция всё ещё удерживала блокировку после списания,
PostgreSQL немедленно вернул бы ошибку. Проверка подтверждает, что блокировка
снята до ожидания уведомления.

HTTP-ответ остаётся незавершённым во время обоих проверочных запросов и приходит
только после завершения отправки. Асинхронный таймер не блокирует event loop,
но `await` удерживает HTTP-запрос примерно три секунды.

Для запросов с ошибками валидации, отсутствующим товаром, недостаточным остатком
и ошибкой БД проверяется отсутствие вызова уведомления.
Существующие проверки rollback и конкурентных заказов проходят с настоящей задержкой.

## Как повторить

Подготовьте `.env` по README и запустите Docker:

```bash
docker compose up -d --wait
npm run test:e2e
cat .tmp/notification-timing.json
```

Для повторения только измерительного сценария:

```bash
npm run test:e2e -- -t 'waits for email after commit'
```

Setup создаёт временную БД и удаляет её после прогона. Файл замеров находится
в игнорируемом Git каталоге `.tmp`; следующие запуски перезаписывают его.

Для ручного наблюдения запустите приложение по README и выполните:

```bash
curl -sS -o /dev/null -w 'HTTP %{http_code}; total %{time_total}s\n' \
  -X POST http://localhost:3000/orders \
  -H 'Content-Type: application/json' \
  -d '{"customerEmail":"user@example.com","items":[{"productId":1,"quantity":1}]}'
```

В каталоге должен оставаться товар. Для успешного заказа ожидаются `201`, время
около трёх секунд и два сообщения `NotificationsService` с одним ID заказа:
`Mock email started for order <id>` и `Mock email completed for order <id>`.

SMTP и брокер сообщений на этом этапе не подключены. Отправка имитируется и
всегда завершается успешно. Обработку сбоев уведомлений рассмотрим отдельно.

## Ответы на вопросы для самопроверки

1. **Зачем отдельный NotificationsService?** OrdersService координирует создание
   заказа, а NotificationsService отвечает за отправку уведомления. Это даёт
   отдельное место для изменения механизма отправки на следующих этапах.
2. **Чем await отличается от consumer?** Сейчас обработчик HTTP ждёт завершения
   метода в том же приложении. Асинхронное ожидание освобождает event loop,
   но ответ остаётся открытым. Consumer обрабатывает задачу отдельно; гарантии
   доставки потребуют настройки брокера и подтверждений обработки.
3. **Что будет при отправке в течение 30 секунд?** HTTP-запрос будет ждать эти
   30 секунд, если раньше не сработает таймаут клиента или прокси. Заказ к этому
   моменту уже закоммичен. В текущем mock ожидание фиксировано на 3000 мс.
4. **Что будет с двумя заказами последней единицы?** Условное списание защищает
   остаток: один запрос создаст заказ, второй получит `409`. Его транзакция
   откатится, уведомление для него не вызовется.
5. **Почему недостаточно убрать await?** Ответ придёт раньше, но незавершённая
   задача останется только в процессе приложения и может потеряться при его
   остановке. Само удаление await не добавляет хранение задачи, повторную доставку
   и подтверждение обработки.
6. **Почему ожидание вынесено за транзакцию?** Открытая транзакция удерживала бы
   соединение и блокировки на всё время отправки. Сейчас заказ фиксируется,
   блокировки снимаются, а затем начинается ожидание уведомления.

Базовое синхронное поведение зафиксировано для сравнения с этапом 2.

## Этап 2, шаг 3 — producer (11 ноября 2026)

Собранное приложение проверено через настоящий HTTP, PostgreSQL и RabbitMQ 4.4.0.
Использованы отдельная временная БД и временный RabbitMQ vhost; оба удалены
после проверки. Основная БД и очереди локального vhost не изменялись.

- Два `POST /orders` вернули `201` за 55 и 8 мс. Без worker в очереди
  `email.notifications` находились два сообщения, число consumer — ноль.
- Проверены `durable: true`, `deliveryMode: 2`, тип `SendOrderConfirmation`,
  уникальность `messageId`, соответствие `orderId` и email сохранённому заказу,
  ISO-формат `createdAt` и совпадение ID в AMQP-свойствах и JSON.
- Недоступность подключения имитировалась заменой AMQP-порта на закрытый порт 1,
  без остановки общего брокера. Следующий запрос вернул `201` за 9 мс;
  заказ доступен через `GET`, сообщение не опубликовано, ошибка зафиксирована
  с `messageId` и `orderId`.
- После восстановления URL следующий запрос занял 8 мс и успешно опубликовался.
  Для четырёх заказов остаток уменьшился с 10 до 6, включая заказ с ошибкой
  уведомления. Автоматической допубликации пропущенного сообщения нет.

Это отдельный локальный замер, а не гарантия задержки. Трёхсекундной работы
consumer в HTTP-пути больше нет; время подключения и publisher confirm остаётся.
Остановка самого брокера, worker, consumer ACK и redelivery здесь не проверялись.

Успешно выполнены `npm run build`, `npm run lint`, `npx tsc --noEmit`,
`npm run test` (6 тестов) и `npm run test:e2e` (48 тестов).
